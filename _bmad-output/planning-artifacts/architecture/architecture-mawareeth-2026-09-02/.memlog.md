- (question) What recovery point is acceptable after total VPS loss: up to 24 hours of database writes via daily dumps, or near-continuous WAL archiving with only minutes of potential loss?
- (decision) Keep the initial one-VPS deployment operationally simple. Defer PostgreSQL WAL archiving, point-in-time recovery, and the complete offsite backup system to a later hardening phase. Initial deployment may be used for validation, but irreplaceable production data must not be accepted until a tested backup-and-restore mechanism is enabled.
- (decision) Application deployments must be zero-downtime using blue/green containers on the single VPS: start the new immutable Django image alongside the current container, wait for its health check to pass, switch Caddy traffic to it, then gracefully drain and stop the old container. A failed health check leaves the old version serving traffic.
- (constraint) Zero-downtime applies to normal application releases only. Because the architecture uses one VPS, host failure, host maintenance, Docker daemon restart, Caddy restart, or incompatible database migration can still cause downtime. Database changes must follow backward-compatible expand/migrate/contract releases.
- (verification) Caddy's current official documentation confirms that caddy reload/API configuration changes are graceful and zero-downtime; invalid new configurations leave the last working configuration active.
