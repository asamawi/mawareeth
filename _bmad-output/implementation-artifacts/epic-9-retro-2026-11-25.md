- **F11 — `_restore_snapshot` decompresses `snapshot_gz` with no size cap. Fix now (security).**
  `api/views.py:264-272` calls `gzip.decompress(base64.b64decode(...))` on an anonymous restore body
  with no bound on the decompressed length, while holding the case write lock. A small compressed
  request can expand to exhaust worker memory (decompression bomb). The compressed request-size limit
  does not bound the decompressed size. Source: `api/views.py:264-272`. Confirmed.

- **F12 — Malformed gzip returns HTTP 500, not the invalid-snapshot refusal. Fix now.**
  The same handler's `except (ValueError, TypeError, binascii.Error, gzip.BadGzipFile,
  json.JSONDecodeError)` does **not** catch `EOFError` (truncated stream) or `zlib.error` (corrupt
  DEFLATE), so those propagate as 500 instead of the promised invalid-snapshot response. The existing
  test `api/test_case_commands.py:539` covers bad-base64 / non-gzip / JSON-string but neither
  truncation nor corrupt DEFLATE (verification-gap VG1). Source: `api/views.py:270`; `api/test_case_commands.py:539`.

- **F13 — `restoreCase` can throw despite its "never throws" contract. Fix now.**
  `web/src/api/case.ts:768-777` builds `snapshot_gz` via `gzipBase64` → `new CompressionStream("gzip")`
  with no try/catch and no plain-`{snapshot}` fallback, so an unsupported runtime or a rejected
  compression stream rejects the promise — but `restoreCase`'s doc and callers (`web/src/interview/flow.ts:875`)
  rely on it always returning an `AnswerResult`. `case.test.ts:410` exercises only the success path
  (VG2). Source: `web/src/api/case.ts:755-777`; `web/src/interview/flow.ts:875`.

- **F14 — "Add relative here" discards a dirty name edit. Fix now (data loss).**
  `edit-sheet.tsx:218` wires `onChoose={entry => onAddHere?.(entry)}` with no draft, while its sibling
  actions pass `dirty ? draftName : undefined` (`onMarkLater`, `onOpenEstate`, `orderQuestion`). The
  pointer handler suppresses the name blur-save, so a successful positioned add closes the sheet and
  loses the typed name. `edit-sheet.test.tsx` tests blur-suppression and positioned-add separately,
  never combined (VG3, missing-adoption). Source: `edit-sheet.tsx:154,218`; `start-case.tsx:731`.

- **F15 — Drag listeners leak if the panel unmounts mid-drag. Fix now.**
  `add-relatives.tsx:96-155` registers window `pointermove`/`pointerup`/`pointercancel` in `press`
  and removes them only in `finish`; there is no unmount cleanup, so a drag left open at teardown
  retains the old callbacks and a later pointer event can fire them against a stale/new estate. The
  drag tests in `add-relatives.test.tsx` all complete before teardown (VG4). Source:
  `add-relatives.tsx:96-155`; `start-case.tsx:673`.

- **F16 — Reported, needs dev confirmation (not re-verified here). Defer.**
  (a) `anonymous_case.py:990` — a relationship/gender edit may not re-validate incident lineage edges,
  leaving tree and calculation inconsistent. (b) `anonymous_case.py:851` — unpositioned/bulk add counts
  only living heirs (`heir_rules.counts(heirs)`), potentially bypassing a placement-cardinality rule
  that also counts `died_before`. (c) `edit-sheet.tsx:154` deletion — the new sheet keeps the name only
  in component state, possibly dropping the prior form's resumable-draft behavior. (d) `family-tree.tsx:137`
  — a long name may overflow the fixed 112 px card. (e) `add-relatives.tsx:138` — the stepper's single
  `maximum` may offer per-entry quantities the server rejects. Each needs a focused check against
  `heir_rules`/`placement_options`, the deleted `heir-form.tsx`, or the card CSS before it is routed.

- **F2 — Capacity gate's contention writer shares the timed write path. Accept + watch.** `api/capacity.py:181`
  runs the contention adversary through the same `self.sample(...)` method the timed actions use
  (`:107`), so any write-path round-trip optimization also speeds the adversary and raises lock
  contention for the timed actions. This is why Story 9.15 shipped **compression-only** (`snapshot_gz`,
  `:252-263`) rather than a round-trip "fold": the fold roughly doubled the adversary's write rate and
  pushed `two_later_deaths` delete/drop/undo over 1000 ms (conflicts ~20→35). The structural coupling
  is real and permanent; it is **accepted** as a property of the gate, with the standing rule that
  write-path latency work must be checked against the contention writer first. Source: `api/capacity.py:107,172-181,252-263`; project memory "Interview capacity gate contention adversary shares the write path."
