- (direction) Distill the repository's final infrastructure architecture into the canonical contract for migrating Mawareeth from Heroku to Hetzner.
- (decision) The final architecture spine is an adopted companion because its diagrams, invariants, stack pins, and operational rules remain load-bearing downstream.
- (capability) CAP-1: Preserve and package the existing Django monolith as an immutable production release; success is a reproducible image passing production deployment checks without a Next.js/DRF rewrite.
- (capability) CAP-2: Operate the application and PostgreSQL on one cost-first Hetzner VPS behind HTTPS; success is private app/database networking with only Caddy publicly exposed and durable state surviving app replacement.
- (capability) CAP-3: Deliver immutable releases through CI with blue-green switching; success is a healthy candidate promoted through production TLS while failures leave the prior release serving.
- (capability) CAP-4: Evolve PostgreSQL safely across overlapping releases; success is serialized committed migrations following expand-migrate-contract without automatic schema rollback.
- (capability) CAP-5: Detect release and host failures operationally; success is dependency-aware readiness, bounded logs, external uptime and disk alerts, and verified operator notification.
- (capability) CAP-6: Rehearse and execute a source-consistent Heroku data, configuration, add-on, and DNS cutover; success is validated restored data and a documented last safe rollback point with no split writes.
- (capability) CAP-7: Make production data recoverable before accepting irreplaceable writes; success is a tested off-host backup restore meeting approved recovery objectives.
- (capability) CAP-8: Reproduce and secure the sole production host and isolate environments; success is a versioned Ubuntu 24.04 baseline with restricted access, protected secrets, and no production data or secrets shared with development, CI, or on-demand staging.
- (constraint) The Heroku exit must preserve the server-rendered Django WSGI monolith and may not require a frontend/backend rewrite or service decomposition.
- (constraint) Phase 1 uses one Hetzner nbg1 VPS as an accepted single failure domain; 99.9% is an observed target, not a redundancy guarantee.
- (constraint) Only CI-produced digest-pinned artifacts may deploy; production builds, mutable branch deployment, self-hosted CI runners, and artifact-embedded secrets are prohibited.
- (constraint) PostgreSQL exclusively owns durable transactional state on a stable external volume and is never publicly reachable.
- (constraint) Public cutover is gated on Django 5.2 LTS, production-safe settings, tested off-host restore, and representative two-slot capacity without swap, OOM, or threshold breach.
- (decision) Non-goals for Phase 1 are application modernization, multi-host high availability, managed PostgreSQL, Kubernetes, Redis/workers, a self-hosted PaaS, permanent staging, and object storage/CDN unless a gated feature requires them.
- (question) What are the source Heroku PostgreSQL version, extensions, locale, size, growth rate, and all attached add-ons/config dependencies?
- (question) Will cutover use a bounded write freeze or replication, and what maintenance-window duration and user-visible behavior are acceptable?
- (question) What backup destination, retention, RPO, and RTO must the tested off-host restore satisfy?
- (question) Which initial Hetzner server size should capacity rehearsal validate against?

- (decision) Cutover uses a planned write freeze with a maintenance page and a 30-minute maximum window; if rehearsal cannot finish within 20 minutes, the runbook must switch to replication before production cutover.
- (decision) Initial production capacity target is Hetzner CX33 in nbg1 with 4 vCPU, 8 GB RAM, and 80 GB NVMe, subject to the representative two-slot capacity gate.
- (decision) Production PostgreSQL uses nightly client-side encrypted Restic backups to a Hetzner BX11 Storage Box with 7 daily, 4 weekly, and 6 monthly retention, a 24-hour RPO, a 4-hour RTO, and an automated monthly isolated restore test.
